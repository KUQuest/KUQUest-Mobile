# Staging API transport contract for current mobile flows

**Research issue:** [KUQUest-Mobile #136](https://github.com/KUQuest/KUQUest-Mobile/issues/136)

**Primary API source:** [staging OpenAPI JSON](https://kuquest-dev-api.kubits.org/openapi/json) (the live document read for this comparison). Route names, methods, security declarations, content types, schemas, and documented status responses below refer to that document. The document's `paths` object starts at line 429 in the fetched JSON; the relevant path keys are at lines 3249, 3396, 3602, 3922, 4760, 4974, and 6203. The OpenAPI repeats the same error envelope for the documented operations: `{ "success": false, "error": { "code": string, "message": string } }`.

## Scope and verdict

This compares only the current mobile transport for **Auth**, **Academic Registration**, **Profile**, **Portfolio**, and **Certificates**. Work Experience is included under Profile because it is part of the current Profile aggregate and is called by the same mobile API. The `src/features/onboarding` directory and `/onboarding` route are UI names retained by the app; transport is assessed by the actual API paths, not those names.

## Observed status handling in current flows

The staging status lists above are the documented operation statuses, not observed live responses. Current mobile handling is:

- `ApiClient` turns every non-2xx response into an `ApiError` with the HTTP status and nested error `code`/`message` when available (`src/api/ApiClient.ts:70-85`).
- A 401 from Academic Registration status causes auth sign-out and `SESSION_EXPIRED` routing (`src/features/auth/AuthService.ts:181-195`). Profile collection reads rethrow 401 rather than treating it as an empty section (`src/api/ProfileApi.ts:27-33`); the live Profile adapter maps 401 to `SESSION_EXPIRED` (`src/features/profile/adapters/liveProfileAdapter.ts:36-47`).
- `ProfileApi.getEditData` catches non-401 collection failures, including a 404, and returns an empty collection plus section-error marker (`src/api/ProfileApi.ts:39-66`). This would hide an absent Experience/Portfolio/Certificates route as a failed/empty section in that editor path.
- The Academic Registration screen only converts an Experience 404 to an empty list; its Certificates and Portfolio calls are direct members of `Promise.all` (`src/features/onboarding/screens/OnboardingScreen.tsx:457-482`). A 404 on either absent collection route therefore reaches the screen's load-error path (`src/features/onboarding/screens/OnboardingScreen.tsx:498-506`).
- The live Profile adapter treats a 404 optional collection as `unsupported` and continues rendering the aggregate (`src/features/profile/adapters/liveProfileAdapter.ts:31-47`). This is a client fallback, not evidence that staging supplies the missing management routes.

## Exact mismatches and unresolved facts

1. **Missing auth operations:** staging components describe native Better Auth payloads and cookie/session shapes, but the live OpenAPI `paths` object has no `/api/auth/*` entries. Exact sign-in, session, and sign-out methods, URLs, statuses, and error responses cannot be validated from this document.
2. **Profile editor sends a field staging rejects:** the editor sends `occupationId` on `PATCH /api/v1/profile`, while staging's `additionalProperties:false` request allows no `occupationId` (`src/features/profileEdit/ProfileEditScreen.tsx:748-757`; staging `updateOwnProfile` request at lines 4240–4380). Occupation is accepted by Academic Registration, not by the documented Profile PATCH.
3. **Profile editor attempts to clear bio:** a blank editor bio becomes `null`, but staging describes Profile values as non-clearable and its PATCH `bio` property is a non-null string (`src/features/profileEdit/ProfileEditScreen.tsx:749-753`; staging Profile PATCH lines 4240–4380).
4. **Current Profile response model omits staging-required `version`:** staging requires `version` in own Profile and avatar mutation data; current Profile types do not model it and current view code never reads it (`src/api/contracts.ts:55-78`; `src/features/profile/adapters/liveProfileAdapter.ts:192-209`). Whether `version` is intended for future concurrency is not stated in the mobile source.
5. **Current stats/review parsers are narrower than staging:** staging permits integer-formatted strings for counts/ratings and nullable review comments; current Zod schemas require numbers and a non-null comment (`src/api/contracts.ts:102-139`; staging Reputation/Reviews paths at lines 4760–5272). A response using any of those documented alternatives can fail mobile parsing.
6. **Avatar response assumption:** staging permits a nullable `fileId` in the successful avatar response, while `StudentApi.uploadAvatar` returns `Promise<string>` and directly returns `body.data.fileId` without schema validation (`src/api/StudentApi.ts:200-213`; staging Avatar POST lines 6384–6736). Upload success with a null file ID is not represented by the current type.
7. **Collection management is absent:** staging has no owner Experience, Portfolio, or Certificates paths, while current registration/profile flows call all of them (`src/api/StudentApi.ts:168-186,216-327`). The public-profile inline arrays are not an equivalent owner CRUD/upload contract.
8. **Academic Registration empty-update edge:** staging requires at least one PATCH property; `AcademicRegistrationUpdate` makes every field optional and the method has no local non-empty guard (`src/api/StudentApi.ts:26-34,134-146`). Normal coordinator calls are populated, but the public method permits a staging-invalid request.
9. **Undocumented idempotency headers:** current persistence sends `Idempotency-Key` values (`src/features/onboarding/profilePersistenceCoordinator.ts:81-102`), but no corresponding parameter is declared on these staging operations. Acceptance and replay semantics are unknown.
10. **Onboarding is not a current API integration:** staging explicitly marks `/api/v1/onboarding/*` as debug scaffolding superseded by Academic Registration. The retained `Onboarding` names in routing/UI do not change the current API paths (`src/features/onboarding/screens/OnboardingScreen.tsx:457-482`; `src/api/StudentApi.ts:124-146`).

## Compatibility conclusion

The mobile transport layer can be traced to the staging contract for the three Academic Registration routes, own Profile reads, Reputation, Reviews, and Avatar at the route/security/envelope level, with the Profile editor field/nullability and narrow numeric parsers called out above. Auth is payload/cookie-compatible by component schema but not verifiable end-to-end because its operations are absent from `paths`. Current Work Experience, Portfolio, and Certificates management cannot be validated against this staging OpenAPI: their owner CRUD and upload operations, encodings, success/error shapes, and statuses are not published. No deprecated Onboarding endpoint is used by the current transport.
