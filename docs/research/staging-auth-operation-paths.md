# Staging Better Auth operation paths

**Research ticket:** [KUQUest-Mobile #142](https://github.com/KUQuest/KUQUest-Mobile/issues/142)

**Question:** Can the staging Better Auth operation paths required by the current native Google sign-in, session lookup, and sign-out flow be verified for `src/features/auth/authClient.ts` and `src/features/auth/AuthService.ts`?

## Scope and evidence rules

This note covers only the three operations used by the current native flow. It does not attempt a browser OAuth callback, admin authentication, or a different mobile authentication protocol. No source/configuration/application file was changed while collecting this evidence.

Primary sources used:

- [Live staging OpenAPI JSON](https://kuquest-dev-api.kubits.org/openapi/json). The line ranges below refer to the pretty-printed response fetched during this research run. Its `paths` object starts at lines 434–435; a direct search of that object found no `/api/auth/*` path key.
- [Live staging API](https://kuquest-dev-api.kubits.org), queried only with unauthenticated, invalid-input, or no-session requests. No real Google ID token or session cookie was used. The invalid token string in the probe was a research placeholder, not a credential.
- Repository source: [`src/features/auth/authClient.ts`](../../src/features/auth/authClient.ts), [`src/features/auth/AuthService.ts`](../../src/features/auth/AuthService.ts), [`src/features/auth/authStorage.ts`](../../src/features/auth/authStorage.ts), [`src/api/contracts.ts`](../../src/api/contracts.ts), and [ADR 0004](../adr/0004-native-google-oauth-with-better-auth.md).
- Installed first-party Better Auth 1.6.26 source, used only to identify library convention—not as evidence that staging is configured identically. The dependency versions are pinned in [`package.json`](../../package.json:5-16).

## Compatibility verdict

**The three routes are live at the expected Better Auth URL, but the staging OpenAPI does not publish them as operations.** Safe live probes verify the native sign-in route's POST validation/error path, the session lookup GET path, and the sign-out POST path. The OpenAPI components independently describe the matching payload and response shapes. Consequently:

- **Native Google ID-token sign-in:** request URL, POST method, and `{provider, idToken.token}` body are compatible with the current mobile call. A successful account sign-in and its `Set-Cookie` response were intentionally not exercised, so end-to-end session creation remains unverified.
- **Session lookup:** `GET /api/auth/get-session` is verified and returns `200 null` without a cookie. The current client convention uses GET. A valid authenticated `{session,user}` response, session refresh, and expiry/error behavior remain unverified.
- **Sign-out:** `POST /api/auth/sign-out` is verified without a session and returns `200 {"success":true}` while expiring secure Better Auth cookies. Authenticated server-side revocation was not exercised. The current app's local cleanup is compatible with the observed cookie names because it accepts both secure and unprefixed forms.

This is a **partial compatibility / incomplete contract** verdict, not evidence that the operations are absent. The live routes exist, while their omission from `paths` prevents formal OpenAPI validation of method lists, request bodies, success responses, and status/error matrices.

## Current mobile operation paths

`authClient` delegates to Better Auth rather than constructing these URLs itself. It passes `EXPO_PUBLIC_API_URL` as Better Auth's `baseURL`, installs `@better-auth/expo` with `SecureStore`, and exposes only the `data`/`error` portions of each result ([`authClient.ts:13-60`](../../src/features/auth/authClient.ts:13-60)). With the staging origin as the configured base URL, the installed Better Auth client resolves the default `/api/auth` base path and appends the operation suffix ([Better Auth `config.mjs:8-25`](../../node_modules/better-auth/dist/client/config.mjs:8-25); [URL resolver `url.mjs:42-49,68-72`](../../node_modules/better-auth/dist/utils/url.mjs:42-49)).

| Mobile operation      | Mobile source behavior                                                                                                                                                                                                                                              | URL and body required by the current flow                                                                                                    |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Native Google sign-in | `AuthService` checks Play Services, obtains a successful native Google response, requires an ID token, applies the local `@ku.th` check, then calls `authClient.signIn.social` ([`AuthService.ts:234-286`](../../src/features/auth/AuthService.ts:234-286)).        | `POST https://kuquest-dev-api.kubits.org/api/auth/sign-in/social` with JSON `{"provider":"google","idToken":{"token":"<Google ID token>"}}`. |
| Session lookup        | `AuthService.getSession()` calls the Better Auth wrapper, returns `null` for no data, and extracts/validates `data.user` for a session ([`AuthService.ts:152-178`](../../src/features/auth/AuthService.ts:152-178)).                                                | Normally `GET https://kuquest-dev-api.kubits.org/api/auth/get-session`, no request body.                                                     |
| Sign-out              | `AuthService.signOut()` starts remote Better Auth sign-out and native Google sign-out concurrently, tolerates either timeout/failure, then deletes the local cookie and session cache ([`AuthService.ts:211-231`](../../src/features/auth/AuthService.ts:211-231)). | `POST https://kuquest-dev-api.kubits.org/api/auth/sign-out`, no request body; the stored Better Auth cookie is sent by the Expo client.      |

The exact app source does not hard-code `/api/auth`; that prefix comes from Better Auth's client resolver. The URL statements above are therefore a combination of the configured base URL, installed-library convention, and the successful live route probes below.

## What the staging OpenAPI describes

The OpenAPI does not list auth operations under `paths`, but it contains Better Auth component schemas:

1. `components.securitySchemes.betterAuthSession` is a cookie API key named `better-auth.session_token`; its description says browsers receive it after successful Google callback and send it with credentials enabled ([OpenAPI lines 57–63](https://kuquest-dev-api.kubits.org/openapi/json)). This is a documented schema-level cookie name, not a declaration for any specific auth operation.
2. `AuthError` contains `message` and optional `code`, with an `INVALID_TOKEN` example ([OpenAPI lines 76–93](https://kuquest-dev-api.kubits.org/openapi/json)). The live 400/401 bodies use exactly those field names, but no auth path response list declares those statuses.
3. `AuthUser` requires `id`, `name`, `email`, `emailVerified`, `firstName`, `lastName`, `createdAt`, and `updatedAt`, with nullable/optional `image`; `AuthSessionResponse` is nested `{session,user}` ([OpenAPI lines 94–199](https://kuquest-dev-api.kubits.org/openapi/json)). The mobile runtime schema requires the same user fields ([`contracts.ts:7-17`](../../src/api/contracts.ts:7-17)), and `AuthService` consumes only the nested `user` member.
4. `SocialSignInRequest` limits `provider` to `google`; when `idToken` is present it requires `idToken.token`. Its description explicitly identifies the native mobile Google Sign-In SDK / `@better-auth/expo` branch and says no authorization URL is returned ([OpenAPI lines 287–374](https://kuquest-dev-api.kubits.org/openapi/json)). This matches the exact mobile body at [`AuthService.ts:274-278`](../../src/features/auth/AuthService.ts:274-278).
5. `SocialSignInIdTokenResponse` describes `{redirect:false, token, user}` and says the Better Auth session cookie is also set ([OpenAPI lines 375–399](https://kuquest-dev-api.kubits.org/openapi/json)). The current app validates `data.user` and does not consume the flat token ([`AuthService.ts:274-286`](../../src/features/auth/AuthService.ts:274-286)). The cookie statement is schema documentation; it was not observed because no valid token was used.
6. `SignOutResponse` describes `{success:true}` ([OpenAPI lines 400–415](https://kuquest-dev-api.kubits.org/openapi/json)), matching the unauthenticated live POST response. No sign-out path or status list is present in `paths`.

The `paths` object begins with `/api/local/test/wallet` at lines 434–435 ([OpenAPI](https://kuquest-dev-api.kubits.org/openapi/json)). A direct path-key search for `/api/auth`, `get-session`, `sign-in`, and `sign-out` returned no auth operation keys. Therefore the component descriptions cannot be promoted to a complete staging operation contract.

The repository ADR records the intended architecture: native Google obtains an ID token, the app passes it to Better Auth, Better Auth owns session/cookie persistence, and custom API requests use the stored cookie rather than a Bearer token ([ADR 0004 lines 1–7](../adr/0004-native-google-oauth-with-better-auth.md)). ## Cookie and transport behavior

### Native sign-in

The Expo plugin sets `credentials: "omit"` for native requests and adds `x-skip-oauth-proxy: true`; it does not attach the existing session cookie for a normal `idToken` sign-in (it only reads one for `link-social`) ([`@better-auth/expo` `client.js:370-383`](../../node_modules/@better-auth/expo/dist/client.js:370-383)). On a successful response, it parses Better Auth `Set-Cookie` headers and persists matching auth cookies in the configured storage ([`client.js:320-339`](../../node_modules/@better-auth/expo/dist/client.js:320-339)). Thus the mobile body is the ID token; the resulting session is expected to arrive through `Set-Cookie`, not a manually persisted Bearer token.

The staging OpenAPI says the cookie is `better-auth.session_token`, while the live sign-out response emitted the secure `__Secure-better-auth.session_token` form. The mobile parser deliberately accepts both token names and both session-data names ([`authStorage.ts:1-35`](../../src/features/auth/authStorage.ts:1-35)). Better Auth's generic HTTPS/production cookie convention prepends `__Secure-` and uses secure/http-only/lax defaults unless overridden ([`cookies/index.mjs:18-49`](../../node_modules/better-auth/dist/cookies/index.mjs:18-49)); this explains the observed prefix as a library convention, but the staging deployment's sign-in cookie attributes still need a valid-session capture.

### Session lookup and sign-out

For requests without an `idToken`, the Expo plugin reads the stored cookie, sets `credentials: "omit"`, adds the cookie plus `expo-origin` and `x-skip-oauth-proxy`, and clears its local session cache when the URL contains `/sign-out` ([`@better-auth/expo` `client.js:384-415`](../../node_modules/@better-auth/expo/dist/client.js:384-415)). The plugin's `getCookie()` serializes stored cookie values for callers ([`client.js:300-318`](../../node_modules/@better-auth/expo/dist/client.js:300-318)). `AuthService` independently deletes `kuquest_cookie` and `kuquest_session_data` after its bounded remote/native sign-out wait ([`AuthService.ts:211-221`](../../src/features/auth/AuthService.ts:211-221)).

The observed staging sign-out response expires three secure cookie names, including `session_data` and `dont_remember`; it does not show whether the mobile runtime receives all repeated `Set-Cookie` headers through its fetch implementation or how the Expo plugin merges them. That is an implementation/runtime unknown, not a route mismatch.

### Session data shape and errors

The OpenAPI's successful session component is nested `{session,user}`. `AuthService` checks the Better Auth wrapper's outer `response.error`, returns `null` for no `response.data`, and validates `response.data.user` against `authUserSchema` ([`AuthService.ts:110-115,152-177`](../../src/features/auth/AuthService.ts:110-177)). The native sign-in path uses the same `data.user` extraction after checking `result.error` ([`AuthService.ts:274-286`](../../src/features/auth/AuthService.ts:274-286)).

Live auth errors are flat `{message,code}` objects, unlike the `{success:false,error:{...}}` envelope used by the separate Student/Profile API client. The current auth service reads `code` and `message` from Better Auth errors ([`AuthService.ts:30-50,159-176,293-307`](../../src/features/auth/AuthService.ts:30-50)), so the observed `VALIDATION_ERROR`, `INVALID_TOKEN`, and `METHOD_NOT_ALLOWED_DEFER_SESSION_REQUIRED` fields are the relevant auth error surface. The complete success/error status matrix is unavailable because auth operations are absent from OpenAPI `paths`.

The local `@ku.th` restriction occurs before the Better Auth request ([`AuthService.ts:268-277`](../../src/features/auth/AuthService.ts:268-277)). The staging schemas constrain `provider` and `idToken`, but do not document that domain policy; server-side enforcement is unresolved.

## Remaining unknowns

1. **Formal operation declarations:** The staging OpenAPI has auth schemas but no `/api/auth/*` path entries. Exact documented methods, request content types, success statuses, and error-status lists are therefore unavailable.
2. **Successful native sign-in:** A real KU account was not used. The 200 response, actual `Set-Cookie` names/attributes, whether the returned flat `token` is needed by this deployment, and whether a newly created user immediately appears in `get-session` are unverified.
3. **Valid session lookup:** Only no-session and invalid-placeholder-cookie responses were observed. The authenticated `{session,user}` values, timestamp serialization, cookie-cache behavior, expiry handling, and whether GET can return `needsRefresh` are unknown.
4. **Refresh POST:** Staging returned 405 for no-cookie POST with a configuration-specific error. A valid near-expiry session might follow a different branch; the current mobile runtime's ability to encounter and complete that branch is unknown.
5. **Authenticated sign-out revocation:** No real session cookie was supplied. The live 200 only proves no-session cleanup; it does not prove database/session-token revocation or the status returned for an expired/invalid signed session.
6. **Cookie prefix and transport:** OpenAPI names `better-auth.session_token`, while staging emits `__Secure-better-auth.*` on sign-out. The app accepts both, but a valid sign-in capture is needed to confirm the exact names, repeated-header handling, expiry attributes, and whether subsequent native fetches send the stored cookie accepted by staging.
7. **Native headers/CORS:** The Expo plugin adds `x-skip-oauth-proxy` and `expo-origin` for non-ID-token requests. The unauthenticated edge response allows credentials but does not establish the complete native header allow-list or trusted-origin policy for a real session.
8. **Error mapping at the client boundary:** Curl observed flat HTTP JSON errors. The Better Auth fetch client is responsible for turning those into `result.error`; no real mobile runtime capture was performed, so exact error object fields exposed to `AuthService` remain unverified even though the service reads `code`/`message`.
9. **Domain enforcement:** The mobile client rejects non-`@ku.th` accounts locally; the OpenAPI does not state whether staging independently enforces the same restriction.

## Conclusion

The current mobile flow points at the conventional and live staging routes:

- `POST /api/auth/sign-in/social` with `{provider:"google",idToken:{token}}`;
- `GET /api/auth/get-session` with no body and a Better Auth session cookie when available; and
- `POST /api/auth/sign-out` with no body and a Better Auth session cookie when available.

Live safe probes verify route reachability, the sign-in POST validation and invalid-token failures, the no-session GET response, the disabled refresh POST response, and no-session sign-out plus cookie expiry. The OpenAPI components support the payload, nested session/user, flat auth-error, and sign-out-success shapes, but the absent `paths` entries mean they are not a complete operation contract. Native request compatibility is therefore **supported for the observed/declared portions, with successful session creation and authenticated lifecycle behavior still unresolved**.
